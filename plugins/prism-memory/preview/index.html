@prism/prism-memory

01核心不变式：缓存前缀字节稳定

每回合的请求是 [系统提示词][工具定义][历史]。这三段是前缀缓存的目标；只要其中任何一个字节变了， 这一整段复用就作废。生态里最常见的记忆插件做法恰恰是「每回合改写 system prompt」或「把 top-k 直接塞进提示词」， 那等于把缓存优势还回去。

本插件的全部动态贡献只有一件事：把召回块作为一条普通 user 消息追加到已准入消息之后。

七条落地纪律

  • 静态 section。系统提示词里只有一段固定的记忆协议（order 2500），文本从配置读取，但不逐回合组装。
  • 无话可说就不输出。没有任何一节有内容时，决策原样返回——该回合与「没装插件」字节相同。
  • 有话说就只说一条。日期、常驻记忆、到期提醒、关键词召回全部合并在同一条消息里，不各发一条。
  • 同输入同字节。渲染是确定性的：全序排序、固定外框、不带生成时间戳，日期也精确到「哪一天」而不是「哪一分钟」。
  • 不重复注入。已注入的 id 由 prismMemory 会话投影从插件自己记录的日志折叠而来。
  • 预算硬顶。整帧受 maxInjectedChars 限制，外框与固定尾注也计入其中。
  • 工具面固定。5 个工具定义；治理命令挂载后新增 0 个 schema。

其中两条是部署决定，出厂默认取的是不变式的强形式：orientationEnabled 默认关（问候是唯一会在「本回合无记忆」时仍开口的贡献， 开它应该是一次选择而不是安装副作用）；identityLayers 默认开，但对旧库惰性——分层轴之前写入的记录不会落在身份层上， 所以升级后的语料注入的字节数与升级前完全一致。

02写入路径与读取路径

记忆写一次、读很多次，而且读发生在延迟敏感路径上。因此重活全部放在写入时：去重、归一、打标、双时间标注。 读取保持同步且无 I/O——记录常驻在 storage domain 的内存态里。

03记忆能力：写入时把重活做完

语料是「一组主张」，不是「一堆同义改写」。三件事在写入时就处理掉，避免后期靠排序去掩盖语料重复。

写入时去重

相似度达到 dedupeReplaceJaccard 的写入视为同一主张，直接复用已有记录并抬高复用计数，不再入库； 达到 dedupeJaccard 的近似改写会被写进去，但把竞争记录一并回给模型，让它决定是否用 supersedes 覆盖。全量保留历史版本，默认只注入当前有效的那条。

双时间与失效而非删除

每条记录带 validAt / invalidAt。supersede、过期、合并、遗忘都走失效语义， 因此「1 月谁是负责人」和「现在谁是负责人」都能回答，旧答案留在库里可审计。

维护流水线

/memory maintain 默认空跑并报告计划：过期记录归档、近重复合并到「读者会保留的那条」 （更高置信度，其次更新）、容量满时淘汰已归档记录、以及报告已断链的 supersede 引用。 加 apply 才落盘，这样一次无人值守的清扫在改数据之前是可检查的。

04七层分类与 BM25 检索

一条主张同时在三个互不相干的轴上归档，每个轴回答一个不同的问题：layer（它讲的是谁的事）、 kind（它是什么类型的陈述）、scope（谁能看见它）。三者拆开之后，召回质量才有提升空间： 同一个「用户偏好」在不同作用域下的价值完全不同。

检索：真 BM25，而不是「看起来像 BM25」

排序是字面 token 上的 BM25（ASCII 词 + CJK 单字与相邻二元组，不需要分词器）。三件事在起作用：词的权重随它在语料里出现得越广而下降， 所以记录是靠「区别于其他记录的部分」被找到的；同一条记录里的重复会饱和，不会让一条记录靠反复说同一个词排到前面； 更长的记录会被折价，所以一句短语在短主张里比埋在一段话中间更容易被召回。

分数按查询词权重之和的平方根归一（而不是直接用和）。这个选择是刻意的：用户的消息很长且大部分是顺带的话， 用总权重做分母会让「命中了唯一重要的那个词」的记录得分和「什么都没命中」一样低。 minInjectScore: 0.6 的语义因此与升级前可比——升级不会悄悄停止召回原本会被召回的东西。

分层轴还带来第二个效果：命中的 rule 与 lesson 排在同样措辞的 fact 之前。 两个旋钮是 bm25K1（词频饱和）与 bm25B（长度归一）；k1: 0 关闭词频加权，b: 0 关闭长度归一。

05自动记忆：沉淀、整理、导入

只靠模型主动调用 memory_remember 的记忆库，长出来的速度取决于模型有多自觉。这里补了三条写入路径， 但它们的共同前提是：任何自动写入都不能把未经复核的主张送进模型。沉淀与导入默认落 pending， 只由 /memory approve 或 /memory reject 定夺。

① 回合沉淀 · 零额外调用

agent/turn-stopping 读刚结束的这一回合——人的那句和助手自己的交代——抽出陈述了持久内容的句子： 约束（must never… / 禁止…）、偏好（I prefer… / 以后都…）、 已确立的成因（the root cause was… / 根因是…）、本工作区的约定。 这条路径里没有模型调用，所以每回合零成本、且对相同文本完全确定——这是它能每回合跑而不是挂在调度器后面的原因。

它也不动复用计数：语料里已有的主张直接跳过，因为 hits 被当成「人真的去拿过这条」的证据， 自动流程抬高它等于造假。

② 梦境整理 · 按窗口

窗口边界取自语料本身（上一条 journal 的写入时间），而不是私有计数器：因此它能跨重启、跨 fork、跨第二个读同一份库的进程。 整理会得出三件事：跨会话被印证的主张（写入路径在「同一主张来自另一个会话」时记下印证数）、同类标签聚成的主题摘要、 以及一条 journal。每日反思只报告已经过完的那一天。

矛盾只上报、不裁决。两条存活主张共享召回标签、措辞重叠却又不是同一个主张时，会被摆到人面前。 在两份主张之间做选择是判断，自动选错的代价比留一个开放问题更大。

③ 跨工具继承 · 有界读取

/memory import 读取按 id 认识的外部布局：claude-code、mimocode、cursor、 以及 workspace（调用方工作区根目录的 AGENTS.md / CLAUDE.md）。 文件的小标题决定层，布局决定作用域。每次读都受文件数、单文件字节数、目录深度三重约束；根目录不存在或目录读不了是正常结果而不是失败—— 那些目录属于别的工具。

不点名就一条都不读（importSources 默认为空），所以不会在用户背后枚举别的工具的记忆。 已经知道的主张计入 skipped 而不重复入库——包括本导入器自己停在待审的那条，以及操作者后来归档掉的那条，避免「退役的主张」被下一次运行复活。

日期与问候

记录可以带一个 dueAt，它与 expiresAt 是两回事：过期让主张退役，到期让主张保持存活、并在日期到来后作为提醒浮出来 （窗口由 reminderWindowDays 控制）。这是本插件全部的提醒面——它是「变得可执行的记忆」，不是调度器。 问候则是一行本地日期、星期与时段，默认关闭；它用「哪一天」而不是「哪一分钟」，否则一个本该相同的回合会因为时间戳而渲染出不同字节。

06跨对话访问：两条腿

只做语义或关键词检索是不够的。真实需求里很大一部分是「上次那个聊 X 的会话里的结论是什么」——这种指代式提问， 检索的落点是会话而不是短语。所以要有两个入口。

① 蒸馏后的 claim：会话是一等维度

memory_conversations 把调用方可见的语料按来源会话分桶，给出每个会话的存活/总数与最新几条； 再用 memory_search 的 conversation 参数窄化到某一个会话。这个参数只能缩小可见集， 不会放大，所以不构成越权面。

② 会话原文：官方检索路径

摘要答不了「原话是什么」。这一半由 session-search.patch.yml 单独挂载官方的 session_search / session_event_read 等 5 个工具，并把 session-query-sqlite 从出厂的内存库 + openAt: never 改成 $DSH_HOME 下的持久 FTS5 索引。成本因此可分离：删掉这一层，记忆行照常工作。

两层之间靠溯源缝合：memory_search 与 memory_conversations 的每一行都渲染来源 session id， 所以一条 claim 可以顺着 id 回到那个会话的原始消息区间。

07治理面：模型工具 vs 人命令

最后一个设计取舍：哪些操作属于模型，哪些必须由人做。把审批、回滚、清扫、导出留在命令行，不只是一种分工， 而是结构性强制——模型没有调用它们的工具，前缀里也不会多出它们的 schema。

判定被放在做出判定的那个操作里：memory_remember 没有「跳过审批」的参数， requireApproval 下写入直接落 pending，而 pending 从不注入。

记忆页走的是同一条结构约束的另一半：页面没有调用会话，因此它经服务的运维面读写 —— operatorRecords、operatorSearch、operatorApprove、operatorReject —— 这些方法不按作用域收窄，每行仍渲染自己的作用域，让收窄在做决定的地方可见。 面向模型的调用方一字未变：工具传自己的 agent，/memory 传自己的会话，两者仍然被它们过滤。

缓存安全那一组测的是什么

  1. 无话可说的回合：没有新增消息，准入的那条原样保留。
  2. 有内容的回合：恰好追加一条，且前缀里的消息是同一个对象引用。
  3. 确定性：固定语料下两次渲染逐字节相同。
  4. 去重：已投递过的记录在同一会话里不会第二次注入。
  5. 预算：整帧长度不超过 maxInjectedChars，含外框与固定尾注。
  6. 工具面：5 个 schema 跨读取字节稳定，挂载治理命令后数量不变。

自动记忆那一组测的是什么

  1. 沉淀：一回合的自述文本被抽成主张、落 pending，且不注入。
  2. 幂等：同一句话两回合不会入库两次，也不会抬高 hits。
  3. 窗口：整理按语料推进而不是计数器，未到窗口时保持安静。
  4. 矛盾：两条主张都存活，整理只把它报告出来。
  5. 常驻：身份层记录在没有关键词命中的首轮也会出现；相关性层则不会。
  6. 导入：dry-run 不落盘；apply 之后作用域、层、来源都正确，重跑计入 skipped。

09已知边界

这一节是设计的一部分，不是免责声明——它标出了下一次该往哪里走，以及当前为什么没去。

  • 没有向量检索。排序是 BM25 上的字面 token（ASCII 词 + CJK 字与二元组）。改写式召回偏弱，没有重排器。harness 目前没有 embedding provider，向量路线需要先有它。
  • 记忆语料没有 FTS 索引。记录放在 storage domain 里并在内存中排序，换来读取同步、模型路径上零 I/O。在 maxRecords 上限之下这是对的取舍；超过该规模、或改写式召回比延迟更重要时，下一步是给同一批记录加 node:sqlite 的 FTS5 索引。
  • 沉淀认的是句式，不是语义。它是一张正则表：换种说法的持久主张会漏掉，读起来像约束却不是的句子会被收进来。两者都正是出厂状态为 pending 的理由。
  • 矛盾检测是启发式的。要求共享召回标签 + 落在相似度区间内，措辞完全不同的矛盾会漏，同一主题下两条各有分寸的主张会被标出来。它只上报，不裁决。
  • 每日反思报告的是前一天。因此它总是在次日出现；一个跨月不跨越本地午夜的会话不会产生反思。
  • 整理跑在回合路径上。整理本身受 dreamWindowRecords 约束，但它是在回合关闭前被 await 的，所以语料很大时「跨过窗口的那一回合」会变慢。
  • 回合末的失败属于该回合。沉淀与整理不吞异常——库坏了应该响。宁可丢掉一次整理也不愿失败一回合的部署，应该在自己的层上加宽捕获。
  • 语料常驻内存。受 maxRecords 约束，但不受字节数约束。
  • hits 只统计显式打开，所以复用权重是弱信号；沉淀刻意不碰它。
  • 维护与整理都没挂调度。它们跑在回合路径与操作者命令上；想要固定时刻执行，需要一条 schedule 行指向 /memory maintain apply 或 /memory dream apply。
  • 页面只新增与结算，不编辑。改写一条主张是带 supersedes 的 memory_remember，驳回一条仍生效的记录是 memory_forget 或 /memory reject；面板两个都不提供，因为在面板上做的编辑没有审计故事。
  • 页面的 overview 在每次写入后读整库。它受 maxRecords 约束，对本存储面向的语料规模是正确的；接近上限的存储需要先做分页读取。
  • 导入布局是按 id 硬编码的。新增一个工具意味着往 IMPORT_SOURCES 加一条；自定义布局没有配置格式。
