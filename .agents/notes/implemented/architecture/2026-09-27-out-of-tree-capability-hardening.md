# Agent Note: Enforce nine advisory capabilities from an out-of-tree bundle

Status: implemented

English | [中文](2026-09-27-out-of-tree-capability-hardening.zh.md)

## Problem

Nine capabilities constrain an agent only through prose. Four are DeepSeek Harness's own: plan mode publishes a deployment-owned prompt section while every tool stays available; the repeat-tool reminder never vetoes a call; the agent loop has no turn budget; and the skill loader's denial names no next step. Five come from the two method packs this fork runs — Ponytail's laziness ladder and Aegis's routing and verification discipline — whose rules reach the model as skill text it is asked to load, with nothing behind the instruction. A deployment that needs one of these enforced has no seam to configure.

Hardening each capability inside its owning package is the direct route and, in this fork, the expensive one. Upstream is synchronized by importing a new tree rather than merging, so an edit to an upstream-owned file or a generated artifact must be replayed by hand at every import, while a new file or package is imported, or not, as a unit.

Plan mode makes that cost concrete. Its owning decision ([plan-specific collaboration state](../simplification/2026-07-22-plan-specific-collaboration-state.md)) rejected a per-plan tool-name allowlist because mutability is a property of each tool rather than a list every plan deployment must maintain, and it left plan mode as guidance rather than enforcement. Adding filtering inside `@deepseek-ai/dsh-plan-mode` would reverse that decision for every deployment, including deployments that want guidance alone.

The method-pack rules have the same ownership problem in a different form. Neither pack is this repository's to change: `plugins/aegis` is an imported upstream pack whose own guide states that it "does not copy skill bodies, replace Harness's model-facing `skill` tool, add a daemon, install a hard pre-tool guard, or claim runtime authority", and its host adapters record a routing miss with an advisory marker rather than preventing it. Admitting an enforcement seam there would contradict a boundary its own ADR records.

## Decision

`plugins/prism-guardrails` is an out-of-tree bundle carrying nine independent rails. Every rail is off until its configuration key names a value, and a key that is present but unusable fails plugin load, so omitting a key is the only way to disable its rail. Each rail registers on a published extension point and owns its decision there.

**Plan mode refuses named tools, in the deployment that asks for it.** `ctx.tools.guard()` refuses the configured tool names while `PlanModeController.get()` reports plan mode active, or selected and still waiting for the next accepted step. A guard rather than a `tools/pre-execute` listener, because guards are evaluated after the whole extensible pre-execute waterfall and have no allow result, so no other plugin's listener ordering can turn the refusal back into permission. The owning package is unchanged: plan mode still publishes guidance and still owns no name list, so a deployment that configures nothing sees exactly the behavior the earlier decision describes.

**A call repeating an identical predecessor goes to approval.** Past a run of `repeatAskAfter` identical consecutive calls, `tools/pre-execute` returns `{ kind: 'ask' }` instead of delegating. Counting lives in `tools/post-execute` because a refused or cancelled call reaches that waterfall too, so a model hammering the gate keeps meeting it and the run length it is told about keeps climbing. `ask` rather than `deny`, because legitimate long runs exist and only a human can separate them from a loop; with no approval channel the fail-closed approval ladder denies the call. An approval does not reset the run, because approvals are `allowed-once`; a claiming user message does, because repetition across a human interjection is not a loop.

**A turn cannot open more steps than the deployment allows.** `agent/pre-step` returns `{ kind: 'reject' }` once the step number exceeds `maxStepsPerTurn`. The judge is the step number the pre-step payload already carries, so retries, refused steps, resume, and fork are correct with no counter to keep, advance, or reset. The loop resets that number when a driver wakes, so the budget is per turn.

**A user-only skill's denial names the way forward.** A model call to the `skill` tool for a catalog entry that is user-invocable but not model-invocable is refused with `ask the user to type /<name> in their next message`. The decision reads the resolved catalog through the public skill registry — the same lookup the tool performs — and a skill that neither interface can invoke keeps the loader's own rejection, because there is no route to offer. The invocation policy itself is unchanged.

**The routing contract refuses the call that broke it.** Aegis asks for a routing decision before the first non-readonly call. Its other hosts append a marker to that call's result, which records the miss after the fact; here `tools/pre-execute` returns `{ kind: 'deny' }` for the first call outside the configured read-only set, unless a decision is already on the record. Two decisions satisfy the contract and both are recorded per session: a call to the `skill` tool, or an assistant message whose text contains `Route: fast-path`. The declaration is read from the committed `assistant/message` session event rather than from the streaming attempt, so a retried or discarded attempt cannot satisfy it, and the record is dropped at `compaction/end`, because the model's next request no longer carries the decision it once made. `Route: fast-path` stays a protocol constant rather than a configuration key: it is the phrase both sides of the method pack agree on, and a deployment that reworded it would be asking the model for a phrase the pack's own skills do not name.

**A turn's write breadth goes to approval.** Past `maxWrittenFilesPerTurn` distinct paths in one turn, `tools/pre-execute` sends the call that would add another to approval. The count is distinct paths rather than writes, because breadth is what an unreviewed turn's diff cannot recover from while repeatedly editing one file is not a breadth risk. Only a call that completed without an error spends the budget: a refused or failed call reaches `tools/post-execute` too, and counting it would let a model exhaust the budget on paths it never wrote.

**A `ponytail:` marker without an upgrade path is refused.** Ponytail's convention is `ponytail: <ceiling>, <upgrade path>`, and the pack's own debt report tags a marker with no trigger as the one that silently rots. A write whose text contains a comment-prefixed marker with nothing after the separator is refused with the convention in the message. Refusing the write is the only point where the fix is free; after the file lands the marker is a debt entry nobody reads. Only comment-prefixed markers count, so prose that merely mentions the convention is not a marker.

**A dependency-manifest write goes to approval.** A write whose last path segment is in `dependencyManifests` goes to approval. Ponytail's ladder puts the standard library, the platform, and an already-installed dependency above a new one, and a manifest write is where that ordering is actually spent; pricing it puts the choice in front of a human at the only moment the alternative is still cheap.

**A turn that wrote without verifying is sent back for evidence.** At `agent/turn-stopping`, a turn that wrote paths and ran no configured verification tool is steered with a message naming the written files and the request for evidence. The stop boundary has no veto — no hook in this harness can refuse the assistant's final text — so the rail uses the machine's own continuation path, the same mechanism `packages/hooks/hooks-claude-code` uses for a blocking `Stop` hook. A completed call to any `verifyTools` tool is the evidence, and a failing check counts: the rail asks whether a check was run, not whether it passed. The turn is interrupted at most once, so a model that ignores the request stops at the next boundary rather than looping.

The rails share one bookkeeping owner. A per-turn record holds the turn number, the written paths, and the verification flag, advanced from the loop's own pre-step payload, so nothing counts turns: the record is reset exactly when the loop opens a turn it has not seen. Written paths are recorded by that owner rather than by the write-budget rail, because the verification gate reads the same set with the write-budget rail off; likewise, a rail that reads written content names no tool of its own, so `writeTools` is one shared configuration list and turning on any such rail without it fails at load rather than loading a rail that can never fire.

The bundle declares one peer dependency. Every harness import in `src/` is `import type` except `createUserMessage` from `@deepseek-ai/dsh-llm`, which the verification gate needs as a value to steer the agent, so the emitted module carries exactly that one external import for the profile to resolve and a deployment installs nothing of its own. Reconciling that with the earlier "imports nothing at all" property was the price of the verification rail; the alternative was fabricating an identified, frozen user message locally, which would drift from the identity and freeze invariants the runtime relies on.

## Alternatives considered

**Harden each capability inside its owning package.** Rejected because the fork replays upstream-owned edits by hand at every tree import, and because the plan-mode rail would reverse a recorded decision for every deployment rather than for the ones that opt in. The owning packages keep their published contracts either way. The same reasoning applies with more force to the two method packs, whose own guides record that they grant no runtime authority and add no hard pre-tool guard.

**Add a new package under `packages/guard/`.** Rejected because it needs a hand-written `tsconfig.base.json` `paths` entry and a workspace install to exist at all, while the bundle's own `tsconfig.json` resolves the checkout's built declarations and its `vitest.config.ts` reuses the checkout's paths facade. A package is the right shape once the repository runner must collect the tests.

**Deny the repeated call instead of asking.** Rejected because legitimate long runs exist — polling one `job_output`, re-reading a file an external process changed — and only a human can tell them from a loop. A refusal removes the choice; an approval prices it, and the fail-closed ladder already produces the refusal where no channel exists.

**Reject the over-budget step inside `agent-loop`.** Rejected because the loop documents that it has no turn budget, and adding one would change the loop contract for every profile. The pre-step waterfall already exposes the step number the loop computed, so the decision belongs to a listener.

**Maintain a per-turn counter for the budget.** Rejected because the step number in the pre-step payload already answers the question, and a counter has to be advanced, reset per turn, and reconciled with retries, refusals, resume, and fork.

**Reset the repeat run when an approval is granted.** Rejected because approvals in this harness are `allowed-once` and are not persisted; resetting would let one decision buy unlimited repetitions of the same call.

**Make plan mode own the denied list.** Rejected for the reason the earlier decision records: the list would then apply to every plan deployment, and it would sit in an upstream-owned file that each import has to replay.

**Bundle the method packs' skills in this plugin.** Rejected because the Aegis tree is already in this checkout at `plugins/aegis/skills`, and a second copy would create the duplicate skill owners and unreliable routing evidence its own install guide warns against. The rails read what the model does; the skills that teach it what to do keep their single owner.

**Keep the routing contract advisory, as the pack's other hosts do.** Rejected because the marker is appended after the call that broke the contract, so it records the miss without preventing it. The tool pipeline is the only seam that can refuse the call, and a contract worth stating is worth enforcing where it can be.

**Deny the unverified turn instead of steering it.** Rejected because no hook can veto the assistant's final text; a refusal has no seam to stand on. Steering at the stopping boundary is the harness's documented continuation path, and the one-step cost bounds it.

**Count writes rather than distinct paths for the write budget.** Rejected because a turn that edits one file repeatedly is not a breadth risk, so pricing it would spend the budget on the shape of the work instead of its size.

**Canonicalize written paths before comparing them.** Rejected because it needs the filesystem resolved against the call's working directory, which would give the write-budget rail a provider dependency it does not otherwise have. The ceiling — `a.ts` and `./a.ts` counting as two — is recorded in the README instead.

**Hand-roll the steering message rather than import `createUserMessage`.** Rejected because the harness factory brands and deep-freezes the message, and a local copy would drift from the identity and freeze invariants the runtime relies on. The repository prefers a maintained dependency over hand-rolling when the dependency genuinely deletes owned code.

## Consequences

Every rail is additive and opt-in, so the owning packages keep their published contracts and their recorded decisions, and a deployment that wants different limits edits one configuration row instead of carrying a package patch across every upstream import. The plan-mode rail is narrower than the allowlist the earlier decision rejected: it names tools to refuse rather than tools to allow, and it reads no tool metadata. A deployment that refuses `write`, `edit`, and `str_replace_editor` still reaches `bash`, because the checkout has no read-only command classifier and denying the shell would also deny the `git status`-class inspection that planning depends on.

The bundle sits outside the repository test runner. `plugins/` is not collected by the checkout's `vitest.config.ts`, so the rails run under the bundle's own config and do not contribute to `pnpm run test` or the per-file coverage gate. Its evidence is an artifact smoke that asserts on the emitted module's text, 85 composed tests against the production tool pipeline, the production agent loop, the real plan-mode controller, the real skill registry, and the loop's own stopping boundary, and four end-to-end runs that boot the shipped `headless` profile through the real Loader with the bundle loaded from its built artifact and assert each rail's enforcement in the resulting session events. Both wiring forms — the shipped package-name row and an overlay naming the built entry — were additionally booted through the `dsh` CLI itself, and each rail's refusal was observed in a real one-shot run: plan mode denies the named tool, the third and fourth identical calls reach the fail-closed approval ladder, a two-step budget ends the turn `blocked` and so exits non-zero in one-shot mode, and the skill loader's denial names the `/name` gesture. The smoke no longer executes the artifact, because the artifact now imports the profile's harness package, which a checkout without a profile install cannot resolve; it asserts on the built file's text instead. The documentation gates do scan the directory, which is why the bundle ships its bilingual README pair.

The repeat rail's `reason` is written for an approver, not for the model. When the approval service reports no channel, the tool registry substitutes its own `requires approval, but no approval channel is available` text, so an unattended deployment refuses the call with the registry's wording; the end-to-end run pins that outcome rather than this bundle's wording. The three `ask`-based rails added here inherit that behavior: write breadth and dependency changes are priced for an approver, and where no channel exists the registry's refusal is what the model reads.

The turn-budget rail trades recoverability for a bound: a refused step is not model-visible, so the log line is the only record of why a turn stopped. The repeat rail has no `include` or `exclude` tool patterns, so a deployment cannot exempt a polling tool from the run count without a further change.

The routing and verification rails are the two that shape a turn rather than price one. A routing refusal costs one round trip and cannot loop, because the model's answer is itself an allowed call. The verification gate can only ask: a model that ignores the steering and stops anyway ends the turn, so the rail's enforcement is one extra step and a stated request, and it does not read the evidence it asked for.
