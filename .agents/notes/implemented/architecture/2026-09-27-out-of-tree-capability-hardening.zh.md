# Agent Note: 在仓库之外用 bundle 强制九项建议性能力

Status: implemented

[English](2026-09-27-out-of-tree-capability-hardening.md) | 中文

## 问题

九项能力只用文字约束 agent。其中四项是 DeepSeek Harness 自带的：计划模式只发布一段部署方拥有的提示词段落，而每个工具仍然可用；重复工具调用提醒从不否决调用；agent loop 没有轮次预算；skill 加载器的拒绝文案不给出下一步。另外五项来自本 fork 所运行的两个方法包——Ponytail 的偷懒阶梯与 Aegis 的路由和验证纪律——它们的规则以"要求模型去加载的 skill 文字"形式抵达模型，指令背后没有任何机制。需要把其中某一项变成强制约束的部署，没有任何可配置的缝。

把每项能力直接加固在它自己的归属包内，是最直接的路线，而在本 fork 里也是最昂贵的路线。上游同步靠"导入一棵新树"而不是 merge，因此对上游拥有的文件或生成物的改动，每次导入都要手工重放；而新增的文件或包则作为一个整体被导入或不导入。

计划模式让这笔成本变得具体。它的归属决策（[计划专用的协作状态](../simplification/2026-07-22-plan-specific-collaboration-state.zh.md)）拒绝了"按计划维护工具名白名单"，理由是可变性是每个工具自身的属性，而不是每个计划部署都要维护的一份清单；该决策把计划模式留作引导而非强制。在 `@deepseek-ai/dsh-plan-mode` 内部加入过滤，会让这项决策对**所有**部署反转，包括那些只想要引导的部署。

方法包规则以另一种形式面对同样的归属问题。两个包都不是本仓库可以改的：`plugins/aegis` 是一个导入的上游方法包，其指南明确写着它"不复制 skill 正文、不替换 Harness 面向模型的 `skill` 工具、不加入常驻进程、不安装硬性前置工具闸门、也不索取运行时权威"，它的各宿主适配器只在事后追加建议性标记，而不是阻止调用。在其中开一个强制缝，会与它自己 ADR 所记录的边界相抵触。

## 决策

`plugins/prism-guardrails` 是一个承载九条相互独立 rail 的仓库外 bundle。每条 rail 在对应配置键给出取值之前都是关闭的，而存在但不可用的键会让插件加载即失败，因此省略键是关闭该 rail 的唯一方式。每条 rail 都注册在文档化的扩展点上，并在那里自行裁决。

**计划模式按名字拒绝工具，且只在主动要求它的部署里生效。** 当 `PlanModeController.get()` 报告计划模式已激活、或已被选择而仍在等待下一个被接受的步骤时，`ctx.tools.guard()` 拒绝配置的工具名。用 guard 而不是 `tools/pre-execute` 监听器，是因为 guard 在整个可扩展的 pre-execute waterfall 之后求值且没有 allow 结果，任何其他插件的监听器顺序都无法把拒绝翻转回许可。归属包保持不变：计划模式仍然只发布引导、仍然不拥有任何名单，因此不做任何配置的部署看到的行为与旧决策所描述的完全一致。

**重复了完全相同前驱的调用送交审批。** 连续 `repeatAskAfter` 次相同调用之后，`tools/pre-execute` 不再放行，而是返回 `{ kind: 'ask' }`。计数放在 `tools/post-execute`，因为被拒绝或被取消的调用同样会走这条 waterfall，持续撞击这道闸门的模型会不断遇到它，而被告知的连续次数也在持续攀升。选择 `ask` 而非 `deny`，是因为合法的长跑确实存在，只有人类能把它们和死循环区分开；在没有审批通道时，故障关闭的审批阶梯会拒绝该调用。审批不重置连续计数，因为审批是 `allowed-once`；而一条主张所有权的用户消息会重置它，因为跨越人类插话的重复不是死循环。

**一轮不能开启超过部署允许的步骤数。** 一旦步骤号超过 `maxStepsPerTurn`，`agent/pre-step` 返回 `{ kind: 'reject' }`。判据就是 pre-step 载荷已携带的步骤号，因此重试、被拒步骤、resume 与 fork 在不需要维护、推进或重置任何计数器的情况下都是正确的。驱动被唤醒时循环会重置该编号，因此预算是按轮计算的。

**"仅用户可调用" skill 的拒绝文案给出行路。** 模型调用 `skill` 工具去加载一个"仅用户可调用、模型不可调用"的目录项时，被拒绝并附上 `ask the user to type /<name> in their next message`。判定通过公开 skill 注册表读取已解析的目录——与工具自身执行的是同一次查找——两种接口都无法调用的 skill 保留加载器自己的拒绝，因为没有任何出路可言。调用策略本身未被改动。

**路由契约拒绝破坏它的那次调用。** Aegis 要求模型在首个非只读调用前给出路由决策。它的其他宿主在该调用结果上追加一个标记，属于事后记录这次失守；这里则由 `tools/pre-execute` 对配置的只读集合之外的首次调用返回 `{ kind: 'deny' }`，除非决策已经落档。两种决策都能满足契约，且都按会话记录：一次对 `skill` 工具的调用，或一条文本包含 `Route: fast-path` 的 assistant 消息。声明从已落档的 `assistant/message` 会话事件读取，而不是从流式尝试读取，因此被重试或被丢弃的尝试无法满足它；记录在 `compaction/end` 时清除，因为模型的下一次请求已不再携带它当初做出的决策。`Route: fast-path` 仍是协议常量而非配置键：它是方法包两侧共同约定的措辞，改写它的部署等于向模型索要一句该方法包自己的 skill 并不提及的话。

**一轮的写盘广度送交审批。** 一轮内不同路径数超过 `maxWrittenFilesPerTurn` 后，`tools/pre-execute` 把会再添一条路径的调用送交审批。计数是不同路径而非写入次数，因为广度才是未经审阅的一轮 diff 无法挽回的东西，而反复编辑同一个文件并不是广度风险。只有未报错完成的调用才会花掉预算：被拒绝或失败的调用同样会走到 `tools/post-execute`，把它计入会让模型在从未写下的路径上耗尽额度。

**没有升级路径的 `ponytail:` 标记被拒绝。** Ponytail 的约定是 `ponytail: <ceiling>, <upgrade path>`，而该方法包自己的债务报告把"没有触发条件"的标记标为会默默腐烂的那一类。写入文本中带有"注释前缀 + 分隔符后为空"的标记时，该写入被拒绝，并在文案里给出约定本身。拒绝写入是修补免费的唯一点；文件一旦落盘，这条标记就是一条没人会读的债务条目。只有带注释前缀的标记才算数，因此仅仅提及该约定的散文不是标记。

**对依赖清单的写入送交审批。** 最后一段路径命中 `dependencyManifests` 的写入送交审批。Ponytail 的阶梯把标准库、平台能力、以及项目已依赖的库放在新依赖之前，而对清单的写入正是这个次序真正被花掉的地方；为这次写入定价，等于在替代方案仍然便宜的唯一时机把它摆到人类面前。

**写了文件却没跑验证的一轮被送回补证据。** 在 `agent/turn-stopping` 处，一轮若写过路径且没有调用任何配置的验证工具，就会被 steer 一条消息，指明写过的文件以及所要的证据。停止边界没有否决权——本 harness 里没有任何 hook 能拒绝 assistant 的最终文本——因此这条 rail 使用机器自身的继续通道，也就是 `packages/hooks/hooks-claude-code` 为阻塞式 `Stop` hook 所用的同一机制。对任一 `verifyTools` 工具的**成功完成**调用即为证据，且**失败**的检查也算数：这条 rail 问的是"有没有跑过检查"，而不是"检查是否通过"。一轮最多被打断一次，因此忽略该请求的模型会在下一个边界停下，而不是陷入循环。

各条 rail 共用同一个记账归属方。一份按轮记录持有轮次编号、已写路径与验证标志，由循环自己的 pre-step 载荷推进，因此这里不数轮次：当循环开启一个记录没见过的轮次时记录恰好被重置。已写路径由该归属方记录，而不是由写盘预算 rail 记录，因为完成验证闸门在写盘预算 rail 关闭时读取的是同一个集合；同理，读取写入内容的 rail 自身不掌握任何工具，所以 `writeTools` 是一份共享配置清单，只开启其中任一 rail 而不声明它会在加载期失败，而不是加载一条永不触发的 rail。

本 bundle 声明一个 peer dependency。`src/` 里每一处 harness 导入都是 `import type`，只有 `@deepseek-ai/dsh-llm` 的 `createUserMessage` 例外——完成验证闸门需要以值的形式用它来 steer agent——因此产物恰好携带这一个外部导入交由 profile 解析，部署本身不需要安装任何东西。与先前"完全不导入任何东西"这一性质调和，是完成验证 rail 的代价；替代方案是在本地伪造一条带身份、已冻结的用户消息，那会偏离运行时依赖的身份与冻结不变式。

## 备选方案

**把每项能力加固在它自己的归属包内。** 被拒，因为本 fork 每次导入上游树都要手工重放上游拥有的改动，而且计划模式 rail 会让一项已记录的决策对所有部署反转，而不只是对主动启用它的部署。两种做法下归属包都保持其已发布契约。同样的理由对两个方法包只会更强——它们自己的指南记录了它们不授予运行时权威、也不加入硬性前置工具闸门。

**在 `packages/guard/` 下新增一个包。** 被拒，因为它需要手写 `tsconfig.base.json` 的 `paths` 条目与一次 workspace 安装才能存在，而本 bundle 自己的 `tsconfig.json` 解析检出目录已构建的声明、`vitest.config.ts` 复用检出目录的 paths 门面。当仓库测试运行器必须收集这些测试时，包才是正确形态。

**直接拒绝重复调用而不是送审。** 被拒，因为合法的长跑确实存在——轮询同一个 `job_output`，或复读一个被外部进程改动的文件——只有人类能把它们和死循环区分开。拒绝取消了选择；审批为它定价，而在没有通道时故障关闭的阶梯本来就会产生拒绝。

**在 `agent-loop` 内部拒绝超预算的步骤。** 被拒，因为该循环文档明说自己没有轮次预算，加入一个会改变所有 profile 的循环契约。pre-step waterfall 已经暴露了循环算出的步骤号，因此这个决定属于监听器。

**为预算维护一个按轮计数器。** 被拒，因为 pre-step 载荷里的步骤号已经回答了这个问题，而计数器必须被推进、按轮重置，并与重试、拒绝、resume 和 fork 一一对账。

**在审批通过时重置重复计数。** 被拒，因为本 harness 的审批是 `allowed-once` 且不被持久化的；重置会让一次决定买下同一次调用的无限次重复。

**让计划模式拥有被拒名单。** 被拒，理由与早先决策记录的相同：该名单届时会作用于每一个计划部署，而且它会落在每次导入都要重放的上游拥有文件里。

**在本插件里内置两个方法包的 skill。** 被拒，因为 Aegis 技能树已经在本检出目录的 `plugins/aegis/skills`，第二份副本会造成重复的 skill 归属方与不可靠的路由证据——这正是它自己的安装指南所警告的失效模式。rail 只读模型做了什么；教模型该怎么做的 skill 保持单一归属方。

**像该方法包的其他宿主那样让路由契约停留在建议层面。** 被拒，因为标记是追加在破坏契约的那次调用之后的，它记录了失守却没有阻止它。工具流水线是唯一能拒绝该调用的缝，而一个值得写下来的契约值得在能强制它的地方被强制。

**拒绝未验证的一轮，而不是 steer 它。** 被拒，因为没有任何 hook 能否决 assistant 的最终文本；拒绝没有可立足的缝。在停止边界 steer 是 harness 文档化的继续通道，而多花一步的代价给它划了界。

**写盘预算按写入次数而不是不同路径计数。** 被拒，因为反复编辑同一个文件的一轮不是广度风险，为它计价等于把预算花在工作形态而不是工作体量上。

**比较前先规范化写入路径。** 被拒，因为它需要用调用的工作目录去解析文件系统，那会给写盘预算 rail 一个它本不需要的 provider 依赖。该上限——`a.ts` 与 `./a.ts` 计为两条——记在 README 里。

**在本地伪造 steer 消息而不导入 `createUserMessage`。** 被拒，因为 harness 工厂会为消息赋予品牌标识并深度冻结它，本地副本会偏离运行时依赖的身份与冻结不变式。当依赖确实能删除自有代码时，本仓库偏好维护中的依赖而非手写实现。

## 影响

每条 rail 都是增量且可选启用的，因此归属包保持其已发布契约与已记录决策，而想要不同限额的部署只需改一行配置，而不必在每次上游导入时携带一份包补丁。计划模式 rail 比早先决策所拒绝的白名单更窄：它列出要拒绝的工具而不是要允许的工具，也不读取任何工具元数据。一个拒绝 `write`、`edit` 与 `str_replace_editor` 的部署仍然到得了 `bash`，因为检出目录没有只读命令分类器，拒绝 shell 会连规划所依赖的 `git status` 一类查看也一并拒绝。

本 bundle 位于仓库测试运行器之外。`plugins/` 不被检出目录的 `vitest.config.ts` 收集，因此这些 rail 在 bundle 自己的配置下运行，也不参与 `pnpm run test` 或逐文件覆盖率门禁。它的证据是：一份对产物文本做断言的 artifact smoke、85 个针对生产工具流水线／生产 agent 循环／真实 plan-mode 控制器／真实 skill 注册表／循环自身停止边界的组合式测试，以及四组端到端运行——通过真实 Loader 启动随附的 `headless` profile、以相对路径从构建产物加载本 bundle，并在产生的会话事件里断言每条 rail 的强制力。两种接线形态——随附的包名行与指向构建入口的 overlay——另外还通过 `dsh` CLI 本身启动过，且每条 rail 的拒绝都在真实的一次性运行中被观察到：计划模式拒绝被点名的工具，第三、四次相同调用触及故障关闭的审批阶梯，两步预算让该轮以 `blocked` 结束从而在一次性模式下非零退出，skill 加载器的拒绝文案指出了 `/name` 手势。smoke 不再执行产物，因为产物现在会导入 profile 的 harness 包，而一个没有 profile 安装的检出目录无法解析它；改为对构建文件的文本做断言。文档门禁确实会扫描该目录，这也是本 bundle 提供中英对照 README 的原因。

重复 rail 的 `reason` 是写给审批人看的，而不是写给模型看的。当审批服务报告无通道时，工具注册表会替换成它自己的 `requires approval, but no approval channel is available` 文案，因此无人值守部署是以注册表的措辞拒绝该调用；端到端运行固定的是这个结果，而不是本 bundle 的措辞。这里新增的三条基于 `ask` 的 rail 继承了同样的行为：写盘广度与依赖变更都是为审批人定价的，在没有通道时模型读到的是注册表的拒绝文案。

轮次预算 rail 用可恢复性换取一个上界：被拒绝的步骤对模型不可见，因此这行日志是"这一轮为什么停下"的唯一记录。重复 rail 没有 `include` 或 `exclude` 工具模式，因此部署无法在不做进一步改动的情况下把某个轮询工具豁免于连续计数之外。

路由与验证这两条 rail 是塑造一轮而非为一轮定价的两条。一次路由拒绝的代价是一次往返，且不会陷入循环，因为模型的回答本身就是被放行的调用。完成验证闸门只能请求：无视 steer 直接停下的模型照样结束该轮，因此这条 rail 的强制力是多一步加上一条明确的请求，而且它并不读取自己所索要的证据内容。
